# Team Lead 与长期小组 Spec

## 背景

MewCode 已有子 Agent 委派与 Git Worktree 隔离，但仍是「主 Agent 中转」的短生命周期任务。多队员并行、彼此直接协作、跨进程恢复上下文、以及让发起方专注协调而不改代码，都还不具备。上一章已提供独立工作目录能力，本步在其上建立长期小组与 Lead 协作。

## 目标

- 主对话默认具备 Lead 能力；与现有子 Agent 委派并存
- 长期小组：名称、负责人、花名册、持久化位置；同时最多一个活跃小组
- 成员可记角色、工作目录（默认独立工作目录，可改为共用主区）、运行后端、是否需要审批
- 运行后端按环境自动选择（独立终端窗格优先，否则同进程轻量运行），不静默降级
- 队员拥有共享任务与邮箱协作能力；主入口与普通子 Agent 不可见这些协作工具
- 需审批者经邮箱结构化计划与批准后再改代码
- Lead 拆分任务、派生成员；全部相关工作完成后用 git 合并各人目录（能解决的冲突则解决，否则回滚并上报）
- 队员自然停下后标记空闲，Lead 发消息即可从磁盘恢复上下文继续指派
- Coordinator：配置能力开关与环境变量两把锁都打开才生效；开启后剥夺 Lead 的写文件能力，保留读与 shell，专注派人、终止、消息与合并

## 功能需求

### 小组生命周期

- F1: Lead 可按名称创建小组。名称合法则在用户目录下建立该小组的持久化位置，写入负责人与空花名册。同名已存在则恢复为当前活跃小组，不覆盖已有花名册与历史任务/邮箱（除非显式解散后重建）。
- F2: 同时最多一个活跃小组。创建或恢复另一个之前，须先停用当前活跃小组（持久化保留，成员进入可恢复的空闲或停止态，不自动解散）。
- F3: Lead 可显式解散活跃小组：停止成员运行、清理运行态，并删除该小组在用户目录下的持久化文件夹。解散后无活跃小组。
- F4: 小组对象至少包含：名称、负责人标识、成员花名册、持久化根路径。成员条目至少包含：名称、角色、工作目录策略（默认独立工作目录，可改为共用主区）、运行后端（由系统按环境选定并记录）、是否需要审批。

### 成员运行

- F5: 派生队员时按环境优先级选择后端：若可用则在独立终端窗格启动完整实例（强隔离）；否则在同进程以轻量方式运行。选定路径实际不可用时，这次派生失败并说明原因，不静默换成另一后端。
- F6: 默认成员工作目录为独立 Git 工作目录；花名册可声明共用主工作区。隔离目录的创建与绑定复用已有工作目录能力。
- F7: 队员自然停止调用工具后，标记为空闲，并通知 Lead。之后 Lead 向其发消息即可从磁盘恢复上下文继续工作，不必重新派生一个新成员实体（同一花名册条目）。
- F8: Lead 可终止指定成员的当前运行；被终止者进入空闲或停止态，花名册条目仍在，除非被移出花名册。

### 协作工具与可见性

- F9: 向队员提供协作工具：共享任务的增删查改（任务可带依赖字段；本步只做记录与展示，不做复杂调度）；以及点对点发消息（含广播）。
- F10: 这些协作工具对主入口上的普通对话工具集、以及普通子 Agent 委派不可见、不可调用。仅活跃小组的 Lead 与队员按角色看到各自允许的工具子集。
- F11: Lead 另有：创建/恢复/解散小组、派生成员、终止成员、读写共享任务、收发消息、在成员完成后发起合并。现有子 Agent 委派工具仍可用。

### 审批

- F12: 花名册标记「需要审批」的队员，在获批前不得执行写文件及会产生改动的等价操作；须先将结构化计划发到 Lead 邮箱。
- F13: Lead 用特定结构的回复（批准或驳回，可带原因）写回该队员邮箱。队员读到批准后方可开始改动类工作；读到驳回则保持不可改动，可再提计划。

### 消息与邮箱

- F14: 点对点消息采用「名称注册表 + 邮箱文件」：先按名称解析到邮箱路径，再写入对方邮箱。独立进程或窗格后端在投递后还须尝试唤醒目标窗格；环境不支持唤醒时消息仍落盘，并说明未能唤醒。
- F15: 支持广播（写入所有其他成员及 Lead 的邮箱）以及若干结构化协议消息（至少覆盖：空闲通知、计划、批准/驳回；可用类型字段区分）。
- F16: 一条消息包含：发件人、正文、时间戳、是否已读、摘要。落盘时自动补时间戳，默认未读。
- F17: 邮箱文件用锁文件保证并发安全；拿不到锁则重试；锁过旧视为过期并可抢占（过期阈值固定约定）。

### 任务与合并

- F18: Lead 可将用户目标拆成带依赖字段的任务写入共享清单，并派生成员。全部相关任务完成后，Lead 用 git 合并各成员隔离目录中的变更；能自动解决的冲突则解决，不能则回滚本次合并尝试并向用户或对话上报。
- F19: 共享任务清单与小组一并持久化，活跃恢复后仍可读写。

### Coordinator 模式

- F20: Coordinator 需两把锁都打开才生效：配置中的能力开关为开，且用户通过约定环境变量主动启用。少一把则行为与未开启相同。
- F21: 生效后：剥夺 Lead（发起方）的写文件类工具；保留读类工具与 shell（以便 git 合并）；Lead 仍可派人、终止、发消息、操作任务与合并。队员是否可写不因该开关被剥夺，仍受审批与自身角色约束。

## 非功能需求

- N1: 邮箱加锁/重试/过期抢占、任务清单读写、名称校验，不依赖真实大模型或真实终端窗格即可用本地文件系统验证。
- N2: 单个队员失败、派生失败或合并冲突回滚，不拖垮 Lead 会话，也不自动解散整个小组。
- N3: 持久化根在用户目录下按小组名隔离；不同小组的邮箱与任务文件互不影响。
- N4: 后端探测结果与「不静默降级」可观测：失败文案须指出曾选定哪类后端、为何不可用。
- N5: Coordinator 双锁状态可查询或在环境提醒中可见，避免用户以为已启用却未生效。
- N6: 从磁盘恢复空闲队员时，须能继续使用其已持久化的对话或工作上下文；恢复失败则说明原因且不创建重名幽灵成员。
- N7: 窗格唤醒失败不丢失已落盘消息；投递结果须区分「已写入」与「已唤醒」。

## 不做的事

- 不做跨机器、跨主机的分布式团队
- 不做成员间实时流式通信；消息以落盘邮箱为准
- 不做复杂的任务依赖调度引擎（依赖字段只存储与展示，不自动阻塞或解锁执行图）
- 不在本步实现多活跃小组并行
- 不把团队协作工具暴露给普通子 Agent 或未按角色授权的调用方
- 不替换或删除现有子 Agent 委派能力
- 不做自动选择后端时的静默降级
- 不保证所有操作系统上都有窗格复用能力；无能力时走同进程路径，二者皆不可用才失败

## 验收标准

- AC1: 按合法名称创建小组后，用户目录下出现该小组持久化位置，含花名册与负责人信息；同名再次创建或恢复不清空已有任务与邮箱。（F1、F4）
- AC2: 已有活跃小组时再激活另一个，须先停用当前；停用后原小组文件仍在，且同时只有一个活跃。（F2）
- AC3: 解散后该小组持久化文件夹被删除，进程内无活跃小组。（F3）
- AC4: 派生队员时：有窗格能力则走独立实例；否则同进程；人为制造选定后端失败时，返回明确失败原因且未改用另一后端。（F5）
- AC5: 默认队员在独立工作目录中改文件，主区同相对路径不受影响；花名册声明共用主区时则写主区。（F6）
- AC6: 队员自然停下后状态为空闲且 Lead 能收到通知；再向其发消息可恢复上下文继续，花名册仍是同一条目而非新建同名队员。（F7）
- AC7: Lead 终止成员后其停止当前运行；条目仍在花名册。（F8）
- AC8: 队员能对共享任务做增删查改（含依赖字段的存取）；主入口工具列表与普通子 Agent 中看不到这些协作工具。（F9、F10）
- AC9: Lead 具备建组、派人、终止、任务、消息、合并相关能力；现有子 Agent 委派仍可调用。（F11）
- AC10: 需审批队员在批准前写文件类操作被拒绝；提交计划后，Lead 批准则之后可写，驳回则仍不可写。（F12、F13）
- AC11: 消息经名称解析写入目标邮箱；字段含发件人、正文、时间戳、已读、摘要；默认未读且有时间戳。广播会进入多名收件人邮箱。（F14、F15、F16）
- AC12: 并发写同一邮箱时不出现文件损坏；锁竞争下最终结果可验证。过期锁可被新写入方取代。（F17）
- AC13: Lead 写入带依赖字段的任务并派人；成员目录有变更后合并：无冲突则主区出现合并结果；制造冲突则合并尝试回滚并有上报说明。（F18、F19）
- AC14: 仅配置开关或仅环境变量时，Lead 仍保有写文件工具；两把都开后写文件工具不可用，读与 shell 仍在，派人、消息、合并仍可用。（F20、F21）
- AC15: 无模型条件下，可用本地目录与锁文件验证建组、邮件、任务、审批状态与合并回滚路径中的文件系统行为。（N1、N2）
