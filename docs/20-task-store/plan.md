# 任务管理与持久化 Plan

## 架构概览

HTTP 服务仍负责接受任务、排队、把一轮交给执行进程，并把执行进程的事件原样送到现有事件流。Task 就是现在的一次执行，标识仍是调用方已经拿到的那个。对话正文继续由执行进程写入工作区的 JSONL。终端会话文件不参与。

运行记录从 JSON 文件换成服务数据目录里的一份 SQLite。服务进程在收到执行进程的事件时，把已经做完的思考、工具调用和助手正文收成 Step，先写入库，再把对应的完成情况送到事件流。文本增量仍立刻进入事件流，不逐条入库。

服务重启后从这份库恢复 Task。未完成的任务按现在的条件重新排队，已记下的 Step 留在库里。执行进程仍是重新打开对话继续，不读取 Step。

| 组件 | 职责 |
| --- | --- |
| 任务库 | 服务数据目录里的一份 SQLite。保存 Task 状态和已完成的 Step。不读取旧的 JSON 运行记录 |
| 任务队列 | 保持现在的接受、排队、取消、续跑和会话忙闲判断。状态的读写改走任务库 |
| 步骤收集 | 在服务进程里把执行进程的事件收成三类 Step。完成的一步先落库，再出现在事件流的完成位置。进行中的内容和不依附于工具的警告不落成 Step |
| 步骤查询 | 按现有任务标识读出已完成的 Step，访问限制与查询该任务相同。执行器停掉时仍可查询 |
| 事件流与聊天页 | 事件种类保持现状。聊天页继续订阅事件流。已有对话列在页面左侧 |
| 执行进程 | 不感知 Task 和 Step。一次性任务与会话一轮的工具、审批、技能、MCP 和钩子保持现状 |

```text
提交一次性任务或会话一轮
  → 任务队列写入 Task
  → 执行进程产生事件
  → 服务进程把做完的思考、工具、正文写成 Step
  → 事件流照常推送
  → 调用方按任务标识读取 Step

服务重启
  → 从任务库恢复 Task 和 Step
  → 未完成的 Task 按现有规则重新排队
  → 执行进程重新打开对话，不重放 Step
```

## 核心数据结构

Task 仍使用调用方现有的 `runId`。库里一行对应一次执行，字段覆盖现在查询任务时能看到的状态，以及续跑所需的排队信息。

### Task

| 字段 | 含义 |
| --- | --- |
| `runId` | 主键，与现在的任务标识相同 |
| `status` | `queued`、`running`、`completed`、`failed`、`cancelled` |
| `workspace` | 工作区 |
| `sessionId` | 对话标识；一次性任务可以没有 |
| `prompt` | 这一次的用户输入 |
| `partialText` | 到目前为止累积的助手正文 |
| `error` | 失败或取消原因 |
| `report` | 结束后的结果报告 |
| `cancelRequested` | 是否已请求取消 |
| `createdAt`、`startedAt`、`endedAt` | 现有时间字段 |
| `timeoutMs`、`sessionsDir` | 执行和续跑所需 |
| `inputCommitted` | 用户消息是否已经写入对话 |
| `attempt` | 已经续跑的次数 |
| `idempotencyKey` | 现有的幂等键，可空 |
| `sessionTurn` | 是否为会话一轮 |
| `resume` | 这一次排队是否跳过重复写入用户消息 |

查询任务的响应字段不变，不把续跑用的内部字段暴露出去。

### Step

按完成顺序从 1 递增。一次 Task 的步骤互不相混。

| 字段 | 含义 |
| --- | --- |
| `seq` | 完成顺序 |
| `kind` | `thinking`、`tool` 或 `text` |
| `text` | `thinking` 是思考摘要，`text` 是这一段助手正文 |
| `tool` | 工具名，仅 `tool` |
| `subject` | 这一次调用的对象，仅 `tool`。执行进程没有带上时为空字符串 |
| `ok` | 成败，仅 `tool` |
| `summary` | 结果摘要，仅 `tool`。不是完整输出 |
| `approval` | 这一次调用已经结束的审批，仅 `tool` 且发生过审批时有。字段与现有审批事件相同，使用现有遮盖 |
| `warnings` | 依附于这一次调用的警告，仅 `tool`。没有则为空 |

未结束的思考、工具或正文不产生行。不依附于工具的警告不产生行。

### 读取步骤

`GET /v1/runs/{runId}/steps`

返回该任务已完成的 Step，按 `seq` 升序。任务不存在时与查询该任务相同。访问限制与查询该任务相同。

细粒度事件只留在当前服务进程的内存里，供这一次进程中的晚订阅使用。库里不另存一份事件流水。服务重启后，事件流对已结束的任务给出结束事件；重启后要看的历史是 Step。

## 模块设计

### 任务库

**职责：** 用服务数据目录里的一份 SQLite 保存 Task 和已完成的 Step。启动时建表。不打开旧的 JSON 运行记录，也不写入它们。

**对外接口：** `load_tasks()` 返回全部 Task。`save_task(record)` 按 `runId` 插入或更新。`append_step(run_id, step)` 追加一条已完成的 Step 并给出 `seq`。`load_steps(run_id)` 按 `seq` 升序返回。库打不开时，这些调用失败，并带上中文原因「任务库不可用」。

**依赖：** 无。不依赖执行进程。

### 步骤收集

**职责：** 挂在一次 Task 的内存里。把执行进程的事件收成 Step，只在一件事做完时交出一条。正文增量先留在内存。下一次工具调用开始前，或这一轮结束前，把已结束的正文交成 `text`。`thinking_end` 交成 `thinking`。`tool_execution_end` 交成 `tool`，带上这段期间附上的审批和警告。工具尚未结束时不交出。没有打开的工具时，警告不交出。

**对外接口：** `observe(event)` 返回零条或一条待落库的 Step。`note_approval(approval)` 和 `note_warning(message)` 只附着，不返回 Step。`flush()` 在一轮结束时交出尚未落库的正文，没有则返回空。

**依赖：** 无。不写库，由任务队列落库。

### 任务队列

**职责：** 接受、排队、取消、续跑和会话忙闲判断保持现状。Task 的读写改走任务库。事件仍先进入本进程内存，供这次进程里的晚订阅使用，不再写入事件文件。完成类事件在发布前，先把步骤收集交出的 Step 写入任务库。服务重启时从任务库恢复；未完成任务的重新排队、次数上限和 `resume` 条件不变。内存里的事件缓冲清空，已记下的 Step 不删。库不可用时拒绝新任务，不回退到 JSON。

**对外接口：** 现有的提交、等待、列出、查询、取消和 `answer_approval` 不变。新增 `steps(run_id)`，任务不存在时与查询该任务相同。

**依赖：** 任务库、步骤收集、现有执行进程客户端。

### HTTP 接口

**职责：** 增加读取步骤的路由，访问限制与查询该任务相同。其余路由不改。健康检查在库不可用时仍可访问。

**对外接口：** `GET /v1/runs/{runId}/steps`。响应是 Step 数组。

**依赖：** 任务队列、现有令牌校验。

### 执行进程

**职责：** 仍不感知 Task 和 Step。工具调用结束事件带上这次权限判断已经算出的对象，供步骤收集写入 `subject`。没有对象时省略，步骤里记空字符串。一次性任务和会话一轮的其余行为不变。

**对外接口：** 现有按行协议。`tool_execution_end` 增加可选的 `subject`。

**依赖：** 现有调度。不读任务库。

### 聊天页

**职责：** 已有对话列在页面左侧。主区域仍是输入和这一轮的事件流。不把 Task 的 Step 画成列表。

**对外接口：** 无新增。左侧项仍是现在的对话，点开后仍读取该对话的消息并订阅事件流。

**依赖：** 现有的对话列表和事件流。不调用步骤查询。

## 模块交互

提交一次执行时，HTTP 接口把请求交给任务队列。任务队列先确认任务库可用；不可用就拒绝，并说明「任务库不可用」，不读取旧的 JSON。可用时写入一行状态为排队的 Task，再进入现在的队列。

轮到它时，任务队列把这一轮交给执行进程。执行进程的事件回到任务队列，按下面的顺序处理：

1. 正文增量立刻进入事件流，步骤收集只把它留在内存里。
2. 思考结束时，步骤收集交出一条 `thinking`。任务队列先 `append_step`，再把该事件送进事件流。
3. 工具调用开始前，若内存里有已结束的正文，先把它写成 `text` 并落库，再发送工具开始。
4. 审批和警告先进入事件流。步骤收集把它们附到当前打开的工具上；没有打开的工具时，警告只留在事件流里。
5. 工具调用结束时，步骤收集交出一条 `tool`。任务队列先落库，再发送工具结束。`subject` 来自执行进程这次结束事件。
6. 这一轮结束时，步骤收集 `flush` 交出最后一段正文。任务队列先落库，再把 Task 标成结束并发送结束事件。

读取步骤时，HTTP 接口调用任务队列的 `steps(run_id)`，任务队列向任务库 `load_steps`。任务不存在时与查询该任务相同。

服务重启时，任务队列 `load_tasks` 恢复全部 Task。已结束的留在库里。未完成的按现在的次数上限和 `resume` 条件重新排队，内存里的事件缓冲清空，已写下的 Step 不删。执行进程重新打开对话，不读取 Step。

聊天页不参加这条链。它仍用现有对话列表和事件流，只是把对话列表放在左侧。

```
server/mewcode_api/
├── task_store.py       — 新建。SQLite 任务库：Task 与 Step 的读写
├── step_collector.py   — 新建。把执行事件收成已完成的 Step
├── run_manager.py      — 修改。状态改走任务库；完成事件先落库再发布；重启从库恢复
├── main.py             — 修改。增加读取步骤的路由
├── models.py           — 修改。步骤响应的字段
├── static/chat.html    — 修改。对话列表放到左侧
└── run_store.py        — 删除。不再读写 JSON 运行记录

src/agent/
└── scheduler.ts        — 修改。工具结束事件带上 subject

server/tests/
├── test_api.py         — 修改。步骤查询、重启仍能读到、旧 JSON 不出现、库不可用
```

运行时的库文件是服务数据目录下的 `tasks.sqlite`。它不进源码树，也不出现在工作区里。

## 技术决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 库 | 使用 Python 自带的 SQLite，文件为服务数据目录里的 `tasks.sqlite` | 满足单一服务库，不增加依赖，也不进工作区 |
| 任务标识 | 继续用现有的 `runId`，不另建一套 | 现有提交、查询、取消和事件流不用改标识 |
| 步骤写在哪里 | 由 HTTP 服务进程收集并落库。执行进程只在工具结束事件上多带 `subject` | 执行进程仍只负责跑一轮；对话正文继续进工作区 JSONL |
| 事件流水 | 只留在当前进程内存，供这次进程里的晚订阅。重启后的历史以 Step 为准 | 文本增量不是 Step，库里不保存第二份流水 |
| 落库时机 | `append_step` 完成之后，才发布对应的完成事件 | 完成事件已经出现在事件流里时，这一步已经可查 |
| 续跑 | 条件、次数上限和是否重复写入用户消息保持现有代码路径。Step 只保留，不送回执行进程 | 续跑仍是重新打开对话，不是重放步骤 |
| 旧 JSON | 删除 `run_store.py` 的调用。磁盘上的旧文件不读、不删 | 新库从空开始，避免把碎事件当成 Step |
| 库不可用 | 新任务直接拒绝，原因是「任务库不可用」。健康检查仍可访问 | 不能假装任务已保存，也不能退回 JSON |
| 聊天页 | 只把现有对话列表移到左侧。不调用步骤查询 | 步骤历史走接口；页面主区域仍是事件流 |
